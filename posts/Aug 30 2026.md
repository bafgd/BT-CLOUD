# My First Post

I'll be explaining each part of my home lab, how they work together, and essentially what I have done so far. I have been working on this since May 2026. There have been some major changes I have made to it over the months that I would like to share.

I have created 3 main services for BTcloud. These are:
- Talk
- Cloud
- AI

Those are the 3 most important services to me. I created BTcloud because I struggled to find a good source that is private, easy to use, genuinely works, and does the 3 main services I needed. After getting nowhere, I just decided to make it myself. The list that follows includes some goals I wanted in this project (this applies to all 3 services):
1. Private (no information goes near any big-tech service)
2. Local (all information is stored on my hardware)
3. Secure (ensure that everything done on BTcloud stays on BTcloud)

Here are some goals that are specific to each service:
> Talk: This has to be secure, e2ee, and have no/low amounts of limits on screensharing quality or anything that has to do with the speed of user's connections. The user's hardware should always be the limit.

> Cloud Drive: This has to be easy to use, easy to share with people, and familiar. This means something like Google Drive or Microsoft OneDrive.

> AI: Instead of just making slop, I wanted to make AI useful in a way that could fit my 3 main goals. Making something similar to JARVIS is what many people think of when running a local, private AI model, but it's not the best idea in my opinion. I focused on making sure that tool usage and the UI itself were proper.

BTcloud first started off as a gimmick. I did not find it useful in any way; the texting server I chose was awful. However, I had created something, somewhere to start. From then on, I decided to make BTcloud mainly private, putting auth walls wherever possible and not advertising services that were private. These include my photos server and my Minecraft server.
Before I begin talking about what I have done, I will list out my setup for this entire system. This will include hardware and software.

### Software:
Here is a list of all the software I use. All of these are open source and run locally on my hardware:
- OpenWebUI (For AI)
- Stoat (For communication)
- OpenCloud (Cloud file storage)
- Immich (Cloud Photos)
- TrueNAS Scale (NAS)
- Linux Server (Main host)
- Kubuntu (Personal desktop, I can use KDE when I want to use the device while also using the power of Linux to run AI models)

### Hardware:
**Linux Box**: This machine runs on Ubuntu Server and is the device that opens up to the network. All other servers in my home network have to route through this device if they want to host anything to the public. This means that if my Linux box were to be breached or taken control of, my personal files would still be safe for some time as they are stored on the other devices that are not exposed to the internet, long enough for me to disconnect the network and stop the threat. This device runs the landing page, the blog posts, the Minecraft server, Stoat server, OpenWebUI, and OpenCloud as of this post. All the data that is stored by all these different servers is only partially stored on this box. For example, my Minecraft server's world files are stored on this machine but are backed up every night to my NAS. The OpenWebUI conversations also follow this same routine.

**NAS**:
This machine runs on TrueNAS Scale. It is the device that holds the largest data pool in the home lab and is also the main central hub for all the data backups. This machine does have some headroom for extra applications that may be run in the future. Currently, it runs no software besides TrueNAS and only has the sole purpose of being a central hub for storage.

**Personal PC**:
This machine runs both Windows 11 for personal computing and Linux, specifically Kubuntu. It is the device that hosts and runs all the AI models and is essentially the core for the AI solution. With the help of Docker, it runs a fork of llama.cpp, ik_llama, and llama-swap.

### Chat
I included chat in this stack because I wanted to create a secure channel for me and my friends to use. This proved to be difficult because many of those secure applications, such as Element (Matrix), had difficult setups. Even after fully setting up these applications, there were other issues such as calls not properly going through Cloudflare and having to pay for a VPS to ensure proper network safety. After that I chose to use the NextCloud stack, which I was using for the Cloud Drive solution but it also included communication. NextCloud Talk was very useful and functioned well, but there were many issues especially with connection of calls. I decided to fall back to REVO or Stoat, which was very basic but it got the job done. It had no encryption so I had to tunnel it through Cloudflare to make sure it was an e2ee chat solution. I've been using REVO since then. The biggest and only issue I have with this app is that there is a hard limit on the screensharing resolution and quality, which I wish had no restrictions.

### Cloud Drive
This was also a huge part of BTcloud that I wanted to get right. I first started off by doing a simple SMB share to see how that would work out. Immediately I had issues with folders and files having different permissions and editing 1 file at the same time wouldn't work out. This caused me to push myself to use NextCloud. At the time, I used NextCloud AIO which included NextCloud Talk, Drive, To-Do, etc. This was very useful and the features were quite frankly exactly what I wanted. The only issue was that the AIO had significant resource usage, which was a big deal for me due to my server having minimal resources. I also faced many issues that I discussed in my Chat problem, with NextCloud Talk having many issues with calls connecting. This led me to go from NextCloud to SeaFile. I used SeaFile for a long time but it still had major issues. I will go from the most significant issue to the least: First, I faced an issue with the connection with SeaFile, then there was a performance issue with the upload and download speeds being stunted due to Cloudflare. I needed an app that can break apart files into multiple chunks to get past Cloudflare. Some good things about SeaFile were the fact that it was robust. Once fully set up, there were no major issues with it that can cause data loss or a significant speed decline. I would highly recommend using SeaFile if you plan on having your Drive only on LAN. However, since I wanted it to have access to the wider internet, I had to find another solution. This led me to OpenCloud, which is what I use to this day. There are some issues with this that I would like to fix, such as upload speeds being stunted and reliability not being as high as NextCloud or SeaFile. The biggest issue is upload speeds and download speeds. Even on LAN, I face reduced speeds due to a small cap on file break size. Essentially, a large file is broken apart into multiple pieces, and OpenCloud forces it to be a small amount, meaning that a large file can have many small pieces of the large file. This causes major slowdowns in upload speeds. I didn't really have a solution to this issue because it was bound to happen with Cloudflare; however, I could do my best to lessen the effects of it. This can be done by making each broken piece of the file be a few MBs less than the max limit of 100MB. This also helps with another issue in Cloudflare where it will disconnect any session/websocket connected for more than a few minutes. By keeping the files broken up, it ensures that most of the data per piece is sent to the destination within a minute and then a new session is started for the next piece. This keeps repeating until the full file is on the destination and then is reconstructed. The only software I found that did this well was, again, NextCloud. The issue I failed to realize early was that the bloated NextCloud feeling was not due to NextCloud itself, but rather the fact that I was using the AIO. This meant that it installed almost everything into one package and ran it all at once, costing significant resource usage. After I realized this, I swapped back to NextCloud and only kept the Files and Drive stack, adding Collabora later. This stack for the Drive solution was far superior to the other ones that I had. Currently my upload speeds are about 5x that of Google Drive. I can edit, make, and share documents, photos, or any files with anyone in the world. I can also collaborate with Collabora on Word docs just like Google Drive. This is getting really close to my full solution that I imagined for the Cloud Drive issue. There are some minor bugs like performance issues and slow loading of Collabora, but that is all tolerable.

### AI
My first iteration of BTcloud started with AI. I was heavily invested in creating LLMs and trying to build my own AI service that I could use to effectively replace ChatGPT and Claude for many general jobs and some advanced jobs. I started by using Ollama with some Gemma and Qwen models. At this stage, things were basic. You could chat with the model, get some information, but it was mostly basic information. Nothing was serious. I explored different models and somehow came to the conclusion that Gemma 4 models were the best. This was later proven very wrong. I made a full lineup of Gemma models with 1 Qwen-Coder model and started testing. I was able to make some basic HTML files that essentially had buttons that linked to common websites such as Google, Wikipedia, Discord, etc. Whilst I was tinkering, I decided that the entire lineup deserved a name. After a few moments, I came up with ORION. Each letter stood for something like O standing for Operational and what not, but I mainly chose the name because I liked how it sounded and the fact that it was space-related. In this ORION lineup, I had ORION-Fast, ORION-Think, and ORION-Code. These 3 are quite self-explanatory. One model was super fast at responding, the next took time to give the best response, and the last was tailored to coding. I gave each a system prompt, and with the basic tool usage at the time provided with OpenWebUI, I continued my testing. This was around the time when I discovered the Qwen3 and Qwen 3.6 lineup in its entirety. After more testing, I came to the right conclusion that these Qwen models, although small, really pack a punch and can genuinely give good responses. I replaced the ORION lineup with the following: ORION-Fast, ORION-Think, and ORION-Code. The fast model had Qwen3-8B, Think had Qwen3.6:27B, and the coder had a Qwen Coder model. This was around the time I discovered that OpenWebUI has advanced parameters for each model, allowing for specific fine-tune controls. I also discovered that the defaults were terrible for Qwen models as there were specific settings that Alibaba (the producers of the Qwen lineup) recommended. After tinkering around with that bit, I was finally getting close to something that was good. Ollama was the backend, OpenWebUI was the front, and it seemed fairly simple and performed well. I used this for a few weeks, but then figured that these models just were not going to cut it for general activities, especially because of how small the context limit was and how slow the responses were, both due to my hardware. I then moved on to using OpenRouter and Groq. This was difficult for me because this would mean that my data and model completion would go online and potentially be seen by others. To combat this, in OpenRouter, I specifically used the option to block those that cache my responses. This gave me some peace of mind that at least not all of my data would be given up once sent. I still use it sparingly with OpenRouter, only asking questions that are not personal. This was an issue because to replace ChatGPT and Claude, I had to get specific, and often that included saying things that I would not want to be used in training data. I then was introduced to llama.cpp and its fork, ik_llama.cpp, by a friend. He also introduced me to llama-swap. I decided to give it a shot, and the first thing that happened after hours of setting up was more failures. I, at the time, couldn't figure out why the server wouldn't boot and run properly. After a week of trying different things, I figured out that my specific AMD card was old and didn't support ROCm. I was stuck with using a ROCm translation layer or Vulkan. I decided to go with the official route of Vulkan to ensure stability through updates. This is when I hit my first major roadblock. ik_llama does not support Vulkan very well as others do. I didn't know this, and for weeks I struggled to understand why I was performing worse in this new software that was supposed to be better than Ollama. I eventually figured out that passing a mainline server command used a Vulkan version that worked with my card. The performance boost I got was phenomenal. I went from 1-4 tokens/sec on an 8B model to almost 40 tokens/sec. This was big because now my models were working double that of Ollama. This was also around the time that I was introduced to MOE models. Essentially these models have a large set of knowledge and work similarly to that of a large model such as a 27B model, but only have 3B, or whatever the model is made to have, active. Qwen3 has an A3B (active 3B) model that I gave a shot at using. With this model, I was able to get around the intelligence of a 27B model at the speeds of an 8B model. This was due to the fact that I had low amounts of VRAM compared to normal RAM, which is where MOE models work the best. Putting the active params on the GPU allowed for fast responses while having the ability to choose across 30B params. With this, I expanded the ORION lineup to what I have now:
- ORION (Local), which uses Qwen3-8B
- ORION-Email (Local), which uses Qwen3-8B
- ORION-Agent (Local), which uses Qwen3-30B-A3B
- ORION-Code (Local), which uses Qwen3-Coder-30B-A3B
- ORION-Think (Local), which uses Qwen3.8-27B
- Backend, which uses Qwen3-0.6B for tasks such as conversation title generation and conversation compression
- ORION-Open (Local), which uses Qwen3.8-27B-Uncensored, a model that has no safeguards or restrictions
- ORION-Fast (Local), which uses Qwen3-8B
- ORION-Flash (Local), which uses Qwen3-0.6B

I also still use some models with OpenRouter as they have some good free models:
- ORION-Code, which uses Groq.Qwen3.6-27B
- ORION-Fast, which uses OR.Minimax-M3
- ORION-Think, which uses OR.Nvidia Nemotron-3-Ultra-550B-A55B
- ORION-RandomModel, which uses the OpenRouter free random model router.

With all of these models, I was finally able to safely leave behind ChatGPT. I am still working on finding a good replacement for Claude, as their Claude Code CLI is amazing and theoretically can hook into LLMs. As of right now, I have not created a personal replacement for Claude and I continue to use it. Many of the skills that Claude uses are downloaded onto my server for the LLMs to use. This wraps up the AI section of my home lab.

### Minecraft Server
The Minecraft Server was not a solution to the 3 fundamental problems I listed, but since I have created it, I will talk about it. This server holds my Forever SMP world with me and my friends. It runs on PaperMC using the itzg Docker container. Added on to this, it has auto sleep and waking of the server to ensure that resources are free for any app that needs it when this server is idle. It is linked to Discord with DiscordSRV and holds many useful plugins like AutoCropReplant and Voxy. Essentially it is a vanilla-like Minecraft Server.
