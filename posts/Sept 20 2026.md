# Making the AI smarter

## The Issue
Since I added the new AI models, I noticed a major issue with my entire stack. Tool calling was poor and the AI was lost every single time. The best way I can explain this was as if the AI was a newborn baby with no knowledge every single time I launch a new conversation. This is a problem because I'm just burning tokens for the AI to use trial and error with tools and eventually get it right. This burns time and RAM usage, both of which are limited.

## Solution
I had a general idea of what could be the issue, and the biggest one I had was related to the system prompt. This is essentially the main prompt that is injected and eventually cached into the start of every conversation, telling the AI all the context it needs to know. Working with Claude, I tested many different System prompts, spending a couple of days, and balancing the token length of each prompt to make sure it's not too much that it overloads the AI, but not too little that I lose performance. I was able to conclude on these prompts.

> On the MoE offloading front there have been several meaningful changes over the last ~9 months:
> 
> - **`--n-cpu-moe` flag** — This is the big one. It lets you split a MoE model's experts across GPU and CPU layers instead of forcing all expert tensors onto GPU memory or entirely on CPU. If a model doesn't fit fully on your GPUs, you can offload *only* some of the expert weights to RAM while keeping the dense layers (and remaining experts) on GPU. This dramatically lowers the VRAM barrier for running large MoE models like Mixtral, Qwen3-MoE, or DeepSeek-V3 variants.
> 
> - **GPU layer assignment automation** (discussed/merged around Dec 2025) — llama.cpp introduced logic to automatically assign whole layers (including their expert sub-layers) to specific GPUs in multi-GPU setups, rather than trying to shard individual tensors across devices. This avoids the "split dense and sparse tensors unevenly" problem that used to cause OOM errors or degraded performance on MoE models.
> 
> - **Multi-GPU & ROCm fixes** — There were a series of bugfixes through mid-to-late 2025 (e.g., issues around KV buffer allocation with `--n-cpu-moe` on ROCm multi-GPU setups, and crashes when offloading very large MoE models via RPC). These landed in subsequent patch releases.
> 
> - **Dense-tensor priority** — The layer assignment logic now prioritizes placing dense tensors first for better overall MoE performance, then fills remaining GPU space with expert layers.
> 
> So the practical takeaway: if you're running a large MoE model and your VRAM isn't enough for all experts on GPU, `--n-cpu-moe` is the key flag to use now — it's been stabilized over the last few releases and works with both CUDA and ROCm.

## New Issue - Slow Output (Closed - Solved)
A new issue arose that I noticed with these repeated tool usages. The main thing I noticed is especially when a model runs a tool, and then runs another tool, the previous output of the tool is not cached, meaning the model has to go over and read the output of its previous tool call while also reading its new tool call. This is fine if it's just 2 tool calls, but it exponentially adds up. I solved this by just simply disabling the `citations` options in OpenWebUI for each model, which then allowed it to cache the search web responses, get url, and other tool calls. This however does get rid of the sources chip at the end of every response, but I did not find that to be a deal breaker.

# Conclusion
The system prompts added to these models made them significantly smarter in tool usage and can now do real work. There is a new issue to tackle and that is the AI models ensuring 100% accuracy and wasting time searching the web over and over again.
